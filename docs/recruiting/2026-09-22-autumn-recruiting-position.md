# NovelForge 秋招作品定位

> 写于 2026-09-22。本文只说明竞争力、不足和打算补上的板块，不代表这些板块已经实现。

## 一句话

NovelForge 要证明的不是“手机上也能聊天”，而是一件长任务可以住在手机里：状态在本地，权限由程序控制，模型只是会犯错的执行者。锁屏、断网、进程被杀之后，任务还能从最后一步继续；模型改不了尚未确认的事实，也删不了正文。

## 现在已经有的竞争力

### 1. 记忆有预算，也有确认边界

`MemorySelector` 不会把全部历史塞进下一次生成。固定样本是 7 个角色、20 条已确认事实、1 条未确认笔记。只留最近 12 条时，本章必须记住的 3 条旧设定召回为 0/3；按本章标题和概要捞回后是 3/3。未确认笔记在两种策略下都不会进入 prompt。

这是程序行为的对照，不是正文质量评分。它能回答“上下文越来越长怎么办”，也能回答“模型自己抽出的笔记为什么不能直接当设定”。

### 2. 长任务能离开页面继续活着

生成前先保存 prompt 快照，再交给 WorkManager。大纲和正文的状态、部分输出、章节修订、模型用量都进 Room。结构化 JSON 中断后从原 prompt 重新生成，避免两段残缺 JSON 拼成非法结果。校验失败进入 `NEEDS_USER`，不静默写进正文。

启动时会清扫进程死亡留下的 `QUEUED` / `RUNNING` 僵尸任务。连续失败会停下来等人处理，不会无限自动重试。

### 3. 本地数据边界是明确的

API Key 只以 Android Keystore 保护的 AES-GCM 密文留在本机，不进备份，也不进日志。用量账本记录输入、输出、缓存和推理 token，还能按模型、项目、用途汇总。故事圣经把已确认事实和待确认事实分开，确认前不进入下一章。

### 4. 写作闭环已经能演示

现在有项目、创作设置、大纲、逐章生成、故事圣经、章节阅读、灵感对话、导出和用量账本。它已经是一个能用的本地 BYOK 写作应用，不是只有接口的样例。

## 不足

### 1. 查书循环还不是 WorkManager 任务

大纲页的查书助手最多走 6 步，只能调用本书的 6 个工具。每一步写入 DataStore，划掉应用后可以点「继续上次」。它还不是 WorkManager 里的一条任务：进程死在某一次模型请求中途时，只能从最后一条已经写下的步骤继续，不能像正文生成那样由系统重新拉起。

### 2. 章节查找还是预算选择，不是按需检索

选择器能把本章点名的角色和旧事实捞回来，但不能根据一个临时问题搜索相隔很远的章节。上下文变长时，只靠每章带最近 12 条事实，仍然会漏掉没有被点名的细节。

### 3. 质量报告没有进入产品

`QualityReport` 和 `QUALITY_CHECK` 还只是模型、枚举和序列化测试。生成完成后没有程序化的连续性检查，矛盾设定主要靠人读。

### 4. 排队还没有按步骤幂等

同一次轨迹里，同一章只会排队一次；模型再点一次会看到「已经排过」。如果进程死在「已经入队、轨迹还没写下」的那一下，恢复后仍可能再排一次。这还不是数据库里的步骤锁。

### 5. 手机端 MCP 目前没有竞争力

让电脑上的客户端连进手机，面试时要回答鉴权、局域网暴露、密钥和正文外流。协议本身不难，也解释不了为什么任务必须住在手机上。

## 打算补上的板块

### 板块 A：一本书的工具权限

已落地，对应 `docs/superpowers/plans/2026-09-22-novel-agent-tools.md` 和 `app/src/main/java/com/novelforge/app/agent/`。

六个工具：搜索章节、阅读章节尾部、读取故事圣经、提议事实、修改大纲、排队写章。

- 搜索最多 5 条，摘录不超过 120 字。
- 阅读只给摘要和不超过 400 字的结尾。
- 待确认事实单独成段，不能冒充已确认事实。
- 提议事实只进 `pendingFacts`，人确认后才进入下一章。
- 改大纲只产生新版本，不删正文。
- 大纲中不存在的章节不能排队。

### 板块 B：六步查书循环

已接到大纲页的「查书助手」。模型每步只能从六个工具里选一个，最多六步。每步写入 DataStore，界面展开后能看到轨迹。划掉应用后用「继续上次」从最后一条已保存步骤接着走。它还没有放进 WorkManager，排队也还没有步骤级幂等。

### 板块 C：规则质检，而不是再请模型打分

先用程序检查已确认事实、待确认事实、章节摘要和大纲之间的明显冲突，再决定要不要让模型解释。质检结果进入现有的 `NEEDS_USER` 状态。没有来源的问题不能自动修改正文。

这一板块用来补“生成完如何发现自己写错”，但它依赖板块 A 的检索和待确认边界，不先做。

## 明确先不做

- 不做无障碍服务去操控其他 App。
- 不在手机上开 MCP 服务。以后如果要做，只能包装同一套 `specs()` 和 `call()`。
- 不先引入向量库。当前规模先把摘录、来源和预算做对。
- 不把 EPUB、TTS、配图、社区或更多 Provider 页面当主线。它们增加功能清单，不增加这篇作品的技术判断。

## 简历口径

现在可以写：

> 本地长篇写作应用。固定记忆名额下，按本章内容捞回旧设定，必须记住的设定召回从 0/3 提到 3/3；未确认笔记不进入 prompt。生成任务、prompt 快照和部分输出持久化，页面关闭或进程重启后可恢复，结构不合法的输出不会写入正文。

查书助手可以另外写一句，但不要写成已经幂等、已经由系统拉起：

> 大纲页的查书助手最多 6 步，只能调用本书的 6 个工具。待确认事实不会进入下一章。每步写入本地轨迹，应用重启后可从最后一条已保存步骤继续。

## 实现顺序

1. 六个工具、Room 适配器和权限测试：已完成。
2. 六步循环和大纲页轨迹：已完成。步骤在 DataStore，不在 WorkManager。
3. 下一步只补排队的步骤级幂等，不先做 MCP。
4. 再做基于来源的规则质检。
